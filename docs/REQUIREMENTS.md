# Requirements Specification & Classification — FindIT

> **Document Status**: `ACTIVE` | **Version**: 1.0  
> **Last Synchronized**: Based on Comprehensive Research & Technical Analysis  

---

## 1. Classification Taxonomy

All requirements and design elements in FindIT adhere to the following strict certainty categories:
- **Confirmed Requirement**: Explicitly agreed and approved functional/non-functional requirement.
- **Proposed Feature / Approach**: Recommended design or feature undergoing evaluation.
- **Constraint**: Mandatory technical, environmental, or security boundary condition.
- **Technical Decision**: Approved implementation mechanism or architectural standard.
- **Ambiguous / Missing Information**: Requirement requiring empirical testing or clarification.
- **Out of Scope**: Explicitly deferred or rejected for the target release.

## 2. Functional Requirements

### 2.1 Workspace & Directory Management
- `REQ-DIR-001` [**Confirmed Requirement**]: The system must allow users to register one or more local directory roots as approved search sources via an OS folder picker.
- `REQ-DIR-002` [**Confirmed Requirement**]: The system must display a list of all registered directories showing directory name, abbreviated path, file count, and last sync timestamp.
- `REQ-DIR-003` [**Confirmed Requirement**]: The system must provide per-directory **Sync** and global **Sync All** operations.
- `REQ-DIR-004` [**Confirmed Requirement**]: Removing a directory from FindIT must strictly delete internal index records (SQLite metadata, FAISS vectors, BM25 tokens) and **never delete, move, or modify physical files on disk**.
- `REQ-DIR-005` [**Confirmed Requirement**]: Overlapping or nested directory registrations must be detected and handled safely to prevent duplicate indexing of identical files.
- `REQ-DIR-006` [**Confirmed Requirement**]: The system must support incremental synchronization by detecting newly added, modified, or removed files using path, file size, and modification timestamps.

### 2.2 Text Extraction & Location Tracking
- `REQ-EXT-001` [**Confirmed Requirement**]: The system must extract text from supported file types: PDF, Markdown (`.md`), Plain Text (`.txt`), Word (`.docx`), PowerPoint (`.pptx`), source code (`.py`, `.ts`, `.js`, etc.), and config files (`.json`, `.yaml`, `.toml`).
- `REQ-EXT-002` [**Confirmed Requirement**]: Text extraction must capture and record granular source-location metadata during parsing rather than attempting retroactive reconstruction:
  - **PDF**: Page number (`Page X`), or an explicit range (`Pages X–Y`) if a chunk crosses boundaries.
  - **PPTX**: Slide number (`Slide N`).
  - **TXT / Code / Config**: Precise 1-indexed line ranges (`Lines X–Y`).
  - **Markdown**: Heading path (`# System > ## Indexing`) and line ranges.
  - **DOCX**: Heading/section path and paragraph index (without fabricating simulated page numbers).
- `REQ-EXT-003` [**Confirmed Requirement**]: Faithful extracted text must be preserved for user inspection to preserve exact casing, punctuation, and code structures.
- `REQ-EXT-004` [**Confirmed Requirement**]: Scanned PDFs lacking an embedded text layer must be flagged as `no_extractable_text` without failing the surrounding indexing job.

### 2.3 Chunking & Passage-Level Indexing
- `REQ-CHK-001` [**Confirmed Requirement**]: The fundamental indexing and retrieval unit must be the **passage (chunk)**, not the entire document.
- `REQ-CHK-002` [**Confirmed Requirement**]: Chunking must be structure-aware, respecting natural boundaries (paragraphs, page boundaries, slide boundaries, function/heading blocks) where possible.
- `REQ-CHK-003` [**Confirmed Requirement**]: Each passage must be assigned a globally unique `chunk_id` linked to a canonical `document_id`.
- `REQ-CHK-004` [**Confirmed Requirement**]: Multiple distinct passages from the same document must be permitted to appear independently in search results if they match the query context.

### 2.4 Hybrid Retrieval & Ranking
- `REQ-RET-001` [**Confirmed Requirement**]: Semantic retrieval must utilize dense vector embeddings generated by `sentence-transformers/all-MiniLM-L6-v2` (384 dimensions) and indexed via FAISS.
- `REQ-RET-002` [**Confirmed Requirement**]: Lexical retrieval must utilize BM25 over extracted passage text.
- `REQ-RET-003` [**Confirmed Requirement**]: For every query, the system must retrieve candidate pools from both FAISS and BM25 (default pool depth: 50 candidates per retriever).
- `REQ-RET-004` [**Confirmed Requirement**]: The system must combine ranked candidate lists using **Reciprocal Rank Fusion (RRF)**:
  $$RRF(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}$$
  with smoothing constant $k=60$.
- `REQ-RET-005` [**Confirmed Requirement**]: The user interface must present a **single, unified ranked list** ordered by RRF score. Technical split sections (Semantic vs. Lexical) must not be shown in the standard user UI.

### 2.5 Search Interface & User Experience
- `REQ-UI-001` [**Confirmed Requirement**]: The homepage must feature a centered search bar, the FindIT branding, and the tagline: *"Find what you remember. Whatever you remember, find where it belongs."*
- `REQ-UI-002` [**Confirmed Requirement**]: Submitting a query via `Enter` must trigger a smooth in-place transition (350–500ms) where the logo and search bar animate into a compact header and the results view slides into place without full-page reloads.
- `REQ-UI-003` [**Confirmed Requirement**]: The submitted query text must remain preserved and editable in the compact header.
- `REQ-UI-004` [**Confirmed Requirement**]: Initial search results must display up to 10 ranked passages, with a "Show more results" action for batch pagination.
- `REQ-UI-005` [**Confirmed Requirement**]: Clicking a result card body must open the in-app **Passage Inspector**, rendering full extracted text and source metadata.
- `REQ-UI-006` [**Confirmed Requirement**]: Clicking the **Open in folder** action must reveal the containing directory in the operating system's native file explorer (with file selection/highlighting where supported) without opening the passage modal.
- `REQ-UI-007` [**Confirmed Requirement**]: The interface must respect `prefers-reduced-motion` settings.

### 2.6 Indexing Progress & Observability
- `REQ-JOB-001` [**Confirmed Requirement**]: The system must provide real-time job progress representing actual pipeline stages (`VALIDATING`, `SCANNING`, `EXTRACTING`, `EMBEDDING`, `INDEXING`, `COMPLETED`, `FAILED`).
- `REQ-JOB-002` [**Confirmed Requirement**]: Progress displays must indicate real counts (e.g., `Processed 42 / 118 files`), never fake simulated percentages.
- `REQ-JOB-003` [**Confirmed Requirement**]: Per-file extraction errors or unsupported formats must be logged and surfaced as job warnings without crashing the overall sync operation.

### 2.7 Primary Terminal Interface
- `REQ-TUI-001` [**Confirmed Requirement**]: FindIT must provide a full-featured Textual TUI as the primary interactive client over the local REST API.
- `REQ-TUI-002` [**Confirmed Requirement**]: The TUI must support search, pagination, passage inspection, native file actions, directory management, sync monitoring, health visibility, and recoverable errors.
- `REQ-TUI-003` [**Confirmed Requirement**]: The TUI must provide explicit keyboard focus, discoverable help, selection persistence, and usable narrow-terminal fallbacks.
- `REQ-TUI-004` [**Confirmed Requirement**]: The TUI may start the backend when unavailable, but may terminate only a backend process that it started itself.
- `REQ-TUI-005` [**Confirmed Requirement**]: Normal user interfaces must display the backend's unified hybrid ordering and must not expose semantic/lexical ranking toggles or client-side re-sorting.

## 3. Non-Functional Requirements

### 3.1 Performance & Latency
- `NFR-PERF-001` [**Constraint**]: Query response time (embedding generation + FAISS query + BM25 query + RRF fusion) must be under **500ms** on standard consumer desktop hardware for a corpus of up to 10,000 passages.
- `NFR-PERF-002` [**Technical Decision**]: FAISS must operate using normalized vectors and `IndexFlatIP` to provide exact inner-product search as a reliable baseline before considering approximate indices (HNSW).
- `NFR-PERF-003` [**Constraint**]: Indexing pipelines must run asynchronously in background workers, ensuring search and UI interactions remain fully responsive.

### 3.2 Security & Data Privacy
- `NFR-SEC-001` [**Constraint**]: The local API must bind strictly to the loopback interface (`127.0.0.1`) and must never listen on external network interfaces (`0.0.0.0`).
- `NFR-SEC-002` [**Constraint**]: The backend must enforce strict path validation, preventing directory traversal (`..`), symlink escapes, or access to files outside approved directories.
- `NFR-SEC-003` [**Constraint**]: Zero user document content or embeddings may be transmitted to cloud services or remote third-party APIs.
- `NFR-SEC-004` [**Constraint**]: Application logs must omit full document text and sensitive user passages.

### 3.3 Reliability & Data Integrity
- `NFR-REL-001` [**Confirmed Requirement**]: SQLite metadata, FAISS vector stores, and BM25 indices must maintain atomic consistency. Deleting or modifying a document must not leave orphaned vector IDs.
- `NFR-REL-002` [**Confirmed Requirement**]: The application must support rebuilding indices from scratch from the SQLite metadata store in the event of index corruption.

## 5. Explicit Constraints & Non-Goals

### 5.1 Project Constraints
- **Single-User Scope**: No multi-tenant architecture, user credentials, or account management systems.
- **Source File Immutability**: Read-only access to user documents. No write, move, or delete operations permitted on source files.
- **Local Model Execution**: Local CPU/GPU inference for embeddings using `all-MiniLM-L6-v2`.

### 5.2 Out of Scope (Deferred to Future Milestones)
- Optical Character Recognition (OCR) for scanned, non-text PDFs.
- Direct PDF viewer highlighting at exact text bounding-box coordinates.
- Continuous background filesystem watchers (`fswatch` / `watchdog`).
- Generative AI answer synthesis or summarization.
- Cloud document backup and synchronization.

### 5.3 Retired Architecture
- The independent `cli/` indexing and retrieval engine, its separate storage directory, and its divergent ranking behavior are retired after the TUI reaches feature parity.
- Native distributable packaging remains deferred; the target is a robust local runtime.
